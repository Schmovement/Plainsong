## Phase 5 contract and test plan (dynamic smart playlists and rule UI) — written BEFORE the implementation

**What the user asked for (original request):** playlists that generate themselves from plays (Most Played), added timestamps (Recently Added) and filter combinations such as Duration > 5:00. Manual playlists stay manual.

**Data model (additive, optional, no DB or backup-format version bump).** A playlist record is `{id, name, ids, created}` today. A smart playlist is the same record plus an optional `rule` object; its `ids` is always `[]` (so an older app that ignores `rule` sees an empty manual playlist, nothing breaks). Members are NOT stored: they are computed from the current library every time they are shown (`S.tracks`, i.e. every saved song, local and saved web). Nothing is seeded: a fresh or legacy library has exactly the playlists it had; presets (Most played, Recently added, Long songs, Top rated, Never played, Heard recently) are templates in the creation dialog only. Opening, listing or viewing playlists writes nothing; no existing song, playlist, queue, like, rating or setting record is created or modified by Phase 5 except the smart playlist the user explicitly saves, renames or deletes.

**Rule grammar (small, explicit, data only, never executed; no eval, no regular expressions, no code, no network).**
`rule = {v:1, match:"all"|"any", conds:[cond × 0..8], sort:{by, dir}, limit}`; `cond = {f, op, v}`; unknown keys, fields, operators or value types anywhere are INVALID. No conditions means the whole library.
- numeric `plays`, `rating` (0..5, unrated = 0, via `ratingOf`), `duration` (whole seconds 0..359999): ops `eq ne gt gte lt lte`, `v` a whole number in range. Duration input accepts `5:00`, `1:02:03` or plain seconds (`Duration > 5:00` = `{duration, gt, 300}`).
- time `added`, `last` (last played): ops `within` / `before` (whole days 1..3650 ago from now); a song with no such time (0/absent, e.g. a saved web song) matches neither op.
- text `title artist album genre`: ops `contains` `notContains` `is`, `v` 1..100 characters after trimming, case-insensitive (`toLowerCase`, no locale folding); a missing genre is the empty text.
- `liked`: op `is`, `v` true/false. `kind`: op `is`, `v` "local"/"web".
- `sort.by` in plays, added, last, duration, rating, title, artist, album; `dir` asc|desc; missing numbers count as 0; EVERY tie, in both directions, breaks by title, artist, then id ascending (deterministic). `limit` 0 (none) or 1..500, applied after sorting.
- name: 1..80 characters after trimming (as for manual playlists).
A rule is validated by ONE function used by the editor (before any write), the strict backup reader and the loader; a stored rule that fails validation is never run (the view says it is damaged and offers Edit, Rename, Delete).

**UI.** "New smart playlist" (sidebar icon button, and a card in Library → Playlists) opens an accessible dialog: name, preset, match all/any (radio group), condition rows (field, operator, value, remove), add condition, sort and direction, limit, a live "N songs match" status, an inline error list; Save is refused with an error when anything is invalid (no write). The smart view shows the rule in words, Edit rule, Rename, Delete, Play/Shuffle; empty states say whether the library is empty or nothing matches. "Add to playlist" and "Remove from this playlist" never apply to smart playlists. Action labels stay unique (lint kept).

**Dynamic behaviour.** Likes, ratings, play counts, metadata edits, removal, import and restore change the visible smart list at once (and after reload). Play all / Shuffle queue a snapshot of the order at the click; later library changes never reorder or edit an existing queue.

**Persistence and safety.** Rule saves use a clone put and apply only `name`/`rule` after the put is durable, queued per playlist id (`trackWrite('pl:'+id)`), re-validating at run time (the playlist must still be the same record and `S.epoch` unchanged; restore/backup busy or locked refuses); a smart delete is queued the same way so it cannot be resurrected by a pending save; a dialog that is still open when a restore replaces the library saves nothing. Manual playlist code paths are unchanged. The documented pre-existing optimistic-like caveat is not touched.

**Backup / restore.** `playlists.json` carries `rule` unchanged (documented in BACKUP_FORMAT.md, additive optional). The strict reader accepts every older archive and rejects, with zero writes, a malformed `rule` (bad version/match/field/op/value/sort/limit/extra key), a rule with a non-empty `ids`, or a rule on a non-object; export → oracle → restore → re-export is identical.

**Test plan (`tests/phase5.test.js`, scenarios Q0..Q10, stable unique canonical check names, selected/finished/aborted lifecycle, ABORT = ERROR).** Q0 no seeding / legacy untouched / viewing writes nothing · Q1 rule engine against an independent harness expectation (every field and operator, boundaries, missing values, case, any/all, empty rule) · Q2 sort both directions, ties, limits · Q3 real-UI create from each preset, edit, rename, delete, reload persistence, raw record shape · Q4 invalid input rejected before any write · Q5 dynamic updates (like, rating, plays, metadata edit, removal, import, restore) · Q6 accessibility (roles, names, keyboard, focus return, empty states) · Q7 queue and playback continuity · Q8 write safety (held save, delete race, epoch change, restore while the editor is open) · Q9 backup/oracle/restore round trip and generated malformed/old archives (accept/refuse with zero change) · Q10 manual-playlist non-regression and menus. Mutants (one safeguard removed each) with a strict classifier like Phase 4's (exact must_fail/must_pass identities, full control coverage, lifecycle, ABORT = ERROR), then candidate ZIP, exact fresh extract of the whole prior matrix + the Phase 5 suite + mutants.

## Phase 5 result (smart playlists; CANDIDATE, not released)

**What it is.** A smart playlist is an ordinary playlist record with `ids: []` plus an additive optional `rule` (`{v:1, match:'all'|'any', conds:[0..8 of {f,op,v}], sort:{by,dir}, limit:0|1..500}`; full grammar and strict-reader rules in `BACKUP_FORMAT.md`, section "Smart playlist rule (Phase 5)"). Membership is computed live from the library at render time and never stored, so it follows likes, ratings, metadata edits, plays, imports, removals, restores and reloads. The only conditions are data (fields plays, rating, duration, added, last, title, artist, album, genre, liked, kind; fixed operator sets); there is no `eval`, no expression language and no external service. Presets (Most played, Recently added, Long songs, Top rated, Never played, Heard recently) are editor templates only: nothing is seeded into the database, no record is created or changed until the person saves. Manual playlists stay manual: smart playlists are excluded from "Add to playlist", `addToPlaylist`/`plRemove` refuse them, and an older app version simply sees an empty manual playlist.

**Rules decided (and tested).** Missing/negative/non-number numeric fields count as 0; rating via `ratingOf`; `within N days` = age at most N whole days, `before N days` = age more than N days, a missing or invalid time matches neither; text conditions are case-insensitive on trimmed 1..100-character values; sort ties always break title, artist, id ascending (descending reverses only the primary key); the limit applies after sorting; one validator (`ruleProblems`) serves the editor, the loader and the strict reader; a damaged rule is never run (the view says so; Rename/Delete stay available; editing starts from a blank rule). The duration field accepts `5:00`, `1:02:03` or seconds. Persistence (`smartCreate/Update/Delete/Rename/Remove`) is queued per playlist through `trackWrite('pl:'+id)`, clones the record, writes, and only then changes memory; it re-validates at run time, checks the library epoch, checks the editor basis (a stale editor refuses to overwrite a newer save), refuses while a backup, restore or database lock is active, and refuses a double submit. Unique action labels (`newSmart`, `smartEdit`, `smartPlay`); the duplicate-case lint in Q0 guards `handleAct`.

### Not verified / real limits of Phase 5 (do not treat as tested)
1. No real screen reader, no real touch device and no real audio output device was used; accessibility is asserted through DOM/ARIA/focus/keyboard checks and mobile-size screenshots in headless Chromium only.
2. "Within/before N days" uses elapsed milliseconds (N x 86,400,000 ms), not calendar days or the person's time zone, and the clock is the device clock; a device with a wrong clock gives wrong lists.
3. Text sort uses the browser's `localeCompare` default locale; ordering of non-ASCII titles may differ between browsers/devices (ties are still deterministic by title, artist, id).
4. No performance measurement on very large libraries; membership is recomputed on render and on a signature change of the member set.
5. Smart playlists are not shared between devices (no sync exists); a backup carries the rule, and an older app reading a new backup ignores it (additive field).
6. Last.fm remains gated (no live account, no secret), audio processing stays local-only, and the dual-local-deck groundwork before crossfade is unchanged.

## Phase 4 result (five-star ratings, library sort/filter; PROMOTED; Phase 5 in progress)

**What it does.** Every song in the library (local and saved web songs; not a search result that is not saved) shows a five-star control in its Songs-list row (hidden below 600 px wide: use the ⋯ menu item `Rate…` / `Rating: ★★★☆☆`, which opens a 0 to 5 star menu). Click a star to set it; click the star the song already has to clear it. Keyboard: Tab reaches ONE star per song (the checked star, or star 1), Left/Right/Up/Down/Home/End move between stars without changing anything (and do not reach the volume/seek shortcuts), Space or Enter sets the focused star, the keys 1 to 5 set that rating, 0, Delete or Backspace clear. The group is a `radiogroup` named "Rating for <title>", each star a `radio` with `aria-checked`; a toast confirms ("Rated … 3 stars", "Cleared"). The Songs toolbar has two new sort orders (`Rating: high to low`, `Rating: low to high`; ties are broken by title, then artist, then id, in BOTH directions, so a tie is never reversed) and a rating filter (Any, Unrated, Rated (1 star or more), 5 stars, 4 stars and up, 3 stars and up, 2 stars and up) that combines with the text filter. A live count line says `N songs` or `n of N songs`; an empty result says which filters match nothing and offers `Clear the filters`. The Liked tab is unchanged (not rating-filtered). Likes are independent in both directions: rating never likes or unlikes a song and liking never changes a rating.

**Data model (also in `BACKUP_FORMAT.md`).** One additive optional field `rating` on a track record: integer 1..5 = stars, 0 = cleared by the user, **absent = never rated** (every legacy record). Absent and 0 display, sort and filter as unrated; the difference exists only in the stored record so a backup/restore returns exactly what was stored. Nothing ever writes the field except the user rating a song: no eager rewrite at start-up, import, sort, filter, backup or restore (proved on the raw database). Setting the value a song already has is a no-op (no write); clearing a never-rated song leaves the field absent. No IndexedDB version bump, no ZIP/format version bump.

**Write path.** `setRating` goes through the existing per-track queue `trackWrite`: at execution time it re-validates (song still the same object, library epoch unchanged, no backup/restore running), takes a `structuredClone` of the stored record, changes ONLY `rating` on the clone, `DB.put`s the clone, and applies the rating to the shared in-memory song only after the store accepted it, so a failed or rejected write leaves nothing behind and cannot leak an uncommitted rating into a like/play/meta/cover writer's snapshot. Rapid clicks: the second click is judged against the SAVED value (two quick clicks on the same star both set that star; they do not set then clear).

**Strict reader and backups.** `rsTrack` (tracks, the saved session's web songs and history snapshots) accepts a missing `rating` and refuses a present one that is not a whole number 0..5 (6, -1, 2.5, "3", null, true/false, arrays, objects, 1e308, 9007199254740993 and the literal -0), with a message naming the field, before anything is written. JSON cannot tell `3.0` from `3` once parsed: `3.0` is accepted as 3 (documented tolerance). The oracle (`tests/oracle_2c.py`) is unchanged: it compares records structurally, the field rule lives in the strict reader and is proven by 24 independently generated archives (`tests/make_rating_archives.py`).

**Review findings fixed in this phase (each reproduced on the unfixed bytes first, then fixed and given a permanent regression scenario R11).**
1. *Dispatch collision.* The first Phase 4 build named the star action `rate`, which already is the playback-speed preset action; the earlier `case 'rate'` silently won and the speed presets stopped working (reproduced: clicking 1.25× left the speed at 1×; `tests/` prior suites were not yet run on that build, the helper-only run of the new suite missed it). Stars now use `rateSong`; R11a clicks 1.5×, a star and 0.75× and asserts speed and ratings stay independent, and statically asserts that `handleAct` has no duplicated action label (31 labels in p3b, 33 now, none duplicated).
2. *Stale queued delete.* `removeTrack` deleted the song from memory and then awaited an unguarded queued `DB.del`; if an earlier write of the same song was slow and a restore replaced the library with the SAME song id before the delete ran, the delete (and the removal's audio/playlist/queue steps) erased the restored song (reproduced with a real restore: song and audio blob missing from the stored library). The queued delete and the removal's continuation are now bound to the library epoch (`if (epoch !== S.epoch)` skip) and the song is re-checked after the confirm dialog. Normal removal behind a slow write is unchanged (R11c).
Pre-existing, NOT changed: `toggleLike` still mutates `liked` in memory before its queued write (p0 behaviour); rating cooperates with it (R7). A rating write whose put was already issued when the library epoch changes may leave the clone in the store (documented, only the memory/result is asserted in R7f).
Test-harness bugs found by the runs (not app bugs, listed so they are not mistaken for app defects): R7d (the seeded cover already equalled the test PNG, a real no-op), R7g (`S.epoch` starts `undefined`, `++/--` gave NaN), R8 (menu entry reads `Rating:` once rated), the refusal text for session/history snapshots, the star detector helper after the action rename (a superseded matrix attempt showed 6 failures from that helper: stopped, raw kept, fixed, re-run), a no-op "click 1.25×" because the seeded session already runs at 1.25×.

**Validation (by bytes, not by name or `File.type`).** At most 8 MiB; PNG/JPEG/GIF/WebP signature and structure walk (PNG exact IEND, JPEG SOF + EOI, GIF trailer, WebP RIFF size); header dimensions 16 to 8192 and at most 40 megapixels checked BEFORE decoding; the browser must decode it with the same size; re-encoded on a canvas to at most 512 px (PNG if there is transparency, else JPEG; at most 700,000 characters for a NEW cover). **Review findings fixed in this phase (both reproduced first on the unfixed bytes, then fixed).**
1. *Write coordination.* IndexedDB snapshots a record when `put()` is called and every writer of a song shares one in-memory object. The first 3B (and 3A) design mutated that object and then awaited the write, so a failing save could leak its uncommitted fields into a like/play/meta/duration writer's snapshot (raw database held the new cover/title while memory had been rolled back), and a rollback could overwrite newer data. Fix: a per-track FIFO (`trackWrite`) for ALL writers and removal; queued writers snapshot when they RUN; `saveCover`/`saveMeta` re-validate when they run, put a clone containing ONLY their own fields, and apply those fields to the shared record only after the write is durable (so a failure has nothing to undo, and nothing stale is written back). Reproduction on the unfixed bytes with a model of IndexedDB's ordering (`GATE` in the suite: one put held, real like + play counter + 3A save + removal interleaved, then rejected or released): S9/S9d/S9e/S10 `113 / 125` with the 12 genuine failures (raw != memory, leaked cover/origCover/title/genre/origMeta, a removed song reported saved, a second queued save refused because memory had been mutated early, S10 x6); after the fix `125 / 125`.
2. *Pending-save semantics.* While Save is in flight the cover editor now shows "Saving…" and Save, Revert, Cancel and Choose image are disabled, the native cancel request and the Escape key are ignored, and a file change is ignored; after a failed save the error stays visible and every control works again. A committed save is never "cancelled". **The 3A info editor's dialog was NOT changed in this respect** (its Cancel/Esc stay usable while its save is pending; its write is correctly coordinated).
Earlier 3B bugs found by the suite itself: `sync()` overwrote the "Reading the picture…" state (real UI bug, fixed); a no-change save was format-checked first (reordered). Test-harness bugs fixed (not app bugs): S5/S6f harness slips; S9 expected the wrong `liked` (L1 is seeded liked); the reload check was split into raw-before == raw-after and memory == raw; the GATE model now also orders deletes; S11's incompressible test noise.
3. *Escape guard (found by REPEATING the pending-save test).* The first pending-save fix listened for Escape on the dialog element. A focused Save button that becomes disabled loses focus, the key then never reached the dialog and the browser sometimes closed the editor during the pending save: S10 passed once and then failed in 2 of 3 repeats. ## Phase 2B design decisions (implemented in 2B; kept here as the record)

1. Replace-only first implementation. Preview (read-only, escaped text, current library vs backup, warnings), then a **separate** confirmation naming what will be erased (checkbox when the current library is non-empty, Cancel focused by default, optional "Back up current library first"). Refuse `complete:false`.
2. One read-write transaction over `tracks`, `playlists`, `blobs`, `kv`: clear the first three, put everything with exact keys, delete only non-`secret:` kv keys not in the backup (this browser's own credentials are kept), verify counts/keys/blob sizes+MIME **inside** the transaction and abort on mismatch. Writes issued synchronously up front; any put error or throw aborts.
3. Before the commit: pause playback, flush session/history, set `DB.lock` so `DB.req` rejects readwrite calls, cancel pending debounced saves, block imports/backups. After a failure: unlock, re-fingerprint the stores (keys + blob sizes) and report truthfully that the old library is unchanged.
4. After the commit: reset `S` completely (tracks/cache/mem/queue/cur/stack/view/lyrics, `loadTok++`, stop both `<audio>` elements, revoke the object URL), reload through a shared `hydrate()` (extract it from `boot`), `restore(ss || {})`, `applyEq()`, cancel saves queued by `load()`, no autoplay. Unlock last.
5. `ps-theme`: written to localStorage only after the IndexedDB commit succeeds; read back to confirm; if the backup has none the current theme is left alone; the result dialog states this is a separate, non-atomic step.
6. Warn that other open Plainsong tabs must be closed (cannot be detected); a crash between the commit and the theme write is possible and documented.
7. Drafted and then reverted in this session to keep 2A write-free: restore buttons (sidebar + top bar), `#restoreIn`, `restore` icon, `DB.lock`, `hydrate`, import/backup guards. Re-add them in 2B.
